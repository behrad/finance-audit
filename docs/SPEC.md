# Receipt Auditor: Spec v0.1

Status: draft for review. Date: 2026-11-05.
Research behind it: `docs/research/payhawk-api.md`, `docs/research/google-adk.md`, `docs/research/gcp-infra.md`.
Fixtures: `fixtures/` (generated by `scripts/make_mock_receipts.py`).

## 1. Goal

Payhawk captures and OCRs receipts but does no semantic or logical validation. This service:

1. Polls Payhawk (REST v3) on a schedule and pulls the expenses plus their receipt files.
2. Extracts each receipt with Gemini, which reads it directly from the image or PDF. There is no separate OCR step.
3. Compares what the receipt says with what was entered in Payhawk.
4. Applies each customer's ruleset, written as a pluggable `SKILL.md`.
5. Publishes the results to a Google Sheet and a web dashboard.
6. Writes fixes and review decisions back to Payhawk.

## 2. Decisions

Decision IDs (D1, D2, …) used below are defined in `docs/DECISIONS.md`, the single source of truth for what is locked. If this spec and that file disagree, `DECISIONS.md` wins.

## 3. Architecture

```
Cloud Scheduler ──► Cloud Run Job "poll"  ─┐       (local: `python -m app.jobs poll`)
Cloud Scheduler ──► Cloud Run Job "decide" ┤
                                           ▼
                    ┌──────────── app (one image) ─────────────┐
                    │ payhawk/   REST client (+ mock server)   │
                    │ pipeline/  ADK Workflow per expense      │
                    │   extract(LLM) → facts(py) → rules(LLM)  │
                    │ skills/    tenant skill registry         │
                    │ store/     Firestore repo                │
                    │ sheets/    gspread upsert + read actions │
                    │ writeback/ patch / status / comment      │
                    │ web/       FastAPI: dashboard + config   │
                    └──────────────────────────────────────────┘
   Firestore (state)   Secret Manager (keys)   GCS (receipts, skills)   Google Sheet
```

- One Docker image serves three roles: `web` (a Cloud Run service behind IAP), `poll` and `decide` (Cloud Run Jobs).
- The jobs don't run inside the web service. When min-instances is 0, Cloud Run throttles the CPU and kills idle instances, which would break in-process cron.

## 4. Data flow per poll

1. **Fetch:** `GET /expenses?$filter={"modifiedAt":{"$greaterThan":"<today-2d>"}}`, paged with `$skip`/`$take` (1000 per page).
   - The date filter ignores time, so it re-fetches a two-day window.
   - Results are deduplicated by `(id, modifiedAt)`.
2. **Skip unchanged:** if an expense has the same `modifiedAt` and the same file IDs as the last run, it is skipped. An expense is re-evaluated whenever it changes.
3. **Download receipts:** for each new or changed expense, download every file in `document.files[]` by `url`, store it at `gs://…/{tenant}/{expense_id}/{fileId}`, and branch on `contentType` (image or PDF).
4. **Run the pipeline** (section 5), which produces a `Review` record.
5. **Save:** upsert the `Review` into Firestore, then upsert the sheet row (section 6).
6. **Write back** (section 7), according to the per-tenant toggles.

Duplicate detection needs the whole tenant history, not just this poll. Each receipt gets a fingerprint `(normalised merchant, receipt number, total, currency, date)`, stored in Firestore. The earliest `createdAt` is the original.

## 5. Pipeline and the pluggable skill

An ADK `Workflow` with three steps. Each step gets a fresh in-memory session, and the inputs are passed as `types.Part.from_bytes` plus a JSON text part.

| Step | Kind | Tenant-pluggable? | Output |
|---|---|---|---|
| `extract` | LlmAgent, `output_schema=ReceiptExtraction` | model only | merchant, receipt/invoice number, date, service period, line items, subtotal/total/currency, card-charged FX line if present, legibility score |
| `facts` | plain Python | which checks run, and their params | deterministic facts: FX deviation %, amount diff, date equality, service-period window vs run month, number equality, supplier vs owner name, duplicate candidates, under-threshold flag |
| `rules` | LlmAgent, `output_schema=Verdict`, no tools, `include_contents="none"` | **yes**: the instruction is the tenant's SKILL.md, plus model choice | `status`, `flags[]`, description per flag, `fixes{}` (supplier/category), `action` + `action_source` |

**Why split the work this way:** arithmetic, date and equality checks run as Python code. The LLM only judges what needs meaning, such as whether the note matches the receipt or the category matches its contents, and it writes the description. That keeps the 2% FX check and the $10 threshold exact instead of left to the model.

**Skill package**, one per tenant, versioned in GCS or uploaded through the UI:

```
skills/<tenant>/<version>/
  SKILL.md          # frontmatter + natural-language rules (the customer's doc, as is)
```
```yaml
---
name: payhawk-default
model: gemini-3.8-flash            # per-tenant override
flags: [duplicate, wrong_exchange_rate, wrong_value, total_mismatch, note_mismatch,
        supplier_not_employee, category_mismatch, date_mismatch,
        service_period_out_of_range, number_mismatch, unreadable_receipt]
checks:                            # deterministic checks from the built-in registry, with params
  duplicate: {}
  auto_approve_under: {amount: 10, currency: USD}
  fx_deviation: {tolerance: 0.02, rate_source: payhawk}
  total_matches_receipt: {}
  supplier_is_employee: {}
  document_date_matches: {}
  number_matches: {}
  service_period: {window: run_month, max_future_days: 30}
categories: [Meals, Travel, Accommodation, Office supplies, Software, Equipment, Learning, Other]
fallback_category: Other
---
<the rules text from "Skill payhawk.docx">
```

**Code seams:**
- **`SkillRegistry.get(tenant) -> Skill`:** loads the skill with ADK `load_skill_from_dir`/`load_skill_from_gcs_dir`, or parses the frontmatter itself if the experimental API shifts, and caches it by `(tenant, version)`.
- **`build_rules_agent(skill) -> LlmAgent`:** the only place where a tenant changes agent behaviour.
- **`CHECKS: dict[str, Callable[[Expense, ReceiptExtraction, Ctx, params], Fact]]`:** a new deterministic rule means adding one function and naming it in a skill.
- **`Verdict.flags`:** validated against the skill's `flags` vocabulary. An unknown flag counts as an error and the row is marked `needs attention`.
- **Governance hook:** ADK `App(plugins=[AuditLogPlugin, PolicyPlugin])`. The plugins log every model call per tenant and can block write-back. Per-agent IAM (Agent Runtime with `AGENT_IDENTITY`) is a later deployment change. The code doesn't change, because the agent factory is already per tenant.

**Not used: ADK `SkillToolset`.** With it, the model decides whether to load the skill. Here the rules must always apply, so the skill text becomes the instruction itself.

## 6. Review record and the Google Sheet

Firestore holds `tenants/{t}/reviews/{expense_id}`, and each sheet row mirrors one review. The columns follow your screenshot and the prototype:

`expense_id, employee, supplier, category, note, document_date, service_start, service_end, document_number, form_amount, form_currency, total_amount, total_currency, receipt_total, receipt_currency, receipt_link, status, category_for_attention, description, action, changes_applied, duplicate_role, duplicate_of, action_source, processed_at, result, skill_version, model, reviewed_at`

Where the Payhawk values come from:

| Column | Payhawk v3 field |
|---|---|
| employee | `owner.firstName + lastName` (fallback `createdBy`) |
| supplier / category / note | `supplier.name` / `category.name` / `note` |
| document_date / document_number | `document.documentDate` / `document.documentNumber` |
| service_start / service_end | `document.serviceDate` / `amortization.startDate`/`endDate` (**see Q2**) |
| total_amount, total_currency | `reconciliation.totalAmount`, `reconciliation.currency` |
| form_amount, form_currency | `reconciliation.baseTotalAmount`, `reconciliation.baseCurrency` |
| receipt_link | dashboard URL `/expenses/{id}`. Raw Payhawk file URLs may need the API key |

How the sheet is written:
- Upserts are keyed by `expense_id`.
- The service **never overwrites `action`**, the column finance edits.
- The `status`/`action` dropdowns and row colouring are created once, in one `batchUpdate`.
- Writes are batched per poll. The Sheets quota is 60 writes per minute for the one service account that all tenants share.

**Multiple flags:** `category_for_attention` holds the main flag. All flags are joined with `; ` in `description`.

## 7. Write-back: what the API allows

Payhawk REST has **no approve/reject endpoint**, and `PATCH` works only while `status=draft`. Each intent maps like this:

| Intent | Trigger | Payhawk call |
|---|---|---|
| Auto-fix supplier/category | `Verdict.fixes`, expense is `draft` | `PATCH /expenses/{id}` with `supplier{id}` / `category{id}`. IDs come from `/suppliers` (find or create a supplier named after the employee) and `/expense-categories`. Logged in `changes_applied` |
| Fix needed but expense already reviewed | same | Becomes a suggestion only (sheet and dashboard). No call |
| "Approve" (auto under $10 when clean, or `action=approve` set by finance) | `decide` job / poll | Apply the pending fixes, then `POST /expenses/{id}/status {"status":"ready"}`, which marks it reviewed. Payhawk's own approvers then approve as usual |
| "Reject" (`action=reject`) | `decide` job | `POST /comments {targetType:"expense", targetId, payload:<flags + descriptions>}`. Status stays `draft` |
| Needs attention, no action yet | poll | One comment with the flag summary, posted once per verdict hash, so finance sees it inside Payhawk |
| Optional: an "AI review" custom field (if the tenant creates one) | poll | `PATCH .../custom-fields/{cfId}` = `clean` / `needs attention: <flags>`, so it can be filtered in Payhawk |

**Per-tenant safety switches:** `writeback.patch`, `writeback.mark_ready`, `writeback.comment`, `writeback.dry_run`.
- All default to on, matching D1, except `dry_run`, which is **on until the first live verification**.
- Every call is logged with request, response and timestamp in `tenants/{t}/writeback_log`.
- Calls are idempotent: a verdict hash is checked before posting comments or status changes.

## 8. Payhawk MCP: verdict

We checked Payhawk's help pages (`payhawk.com/help/connecting-payhawk-mcp`, `payhawk-mcp-overview`). Logging in once and letting our agent drive the MCP in the background doesn't work today:

- **Client allowlist:** "Payhawk accepts sign-ins only from the AI Assistants in the table". Any other app gets `host-not-allowed` or "client redirect URI is not allowed". Gemini and ADK aren't on the list. Pretending to be a listed client (for example, reusing Claude's redirect URI) would break Payhawk's terms, so we won't do it.
- **Session lifetime:** the login expires after 7 days without use and after 30 days at most, so someone would have to log in again every month.
- **Confirmation:** "Every change shows a preview first and waits for your explicit confirmation." The confirmation is meant to come from a person.

**Path forward:**
1. Email support@payhawk.com and ask them to allowlist our OAuth client. Their docs give this as the route for unlisted apps.
2. Keep a `PayhawkClient` interface with only the REST implementation in v1. If Payhawk allowlists us, an `McpPayhawkClient` adapter (ADK `McpToolset` with `header_provider`) can add `approve_or_return`. Our dashboard's confirm button would count as the human confirmation. Nothing else in the code changes.

## 9. Web app (FastAPI)

- **`/`, the dashboard:**
  - Based on the `standalone.html` prototype: filter chips, search, a table, and a drawer with the receipt image, Payhawk fields and receipt extraction side by side, flags, and action buttons.
  - Pages are server-rendered with plain JS. There is no SPA build.
  - The dashboard and the sheet write the same `action` field. Whichever was changed most recently wins: the sheet is read in the `decide` job, and the dashboard writes immediately.
- **`/settings`, the configuration page (per tenant):**
  - Payhawk account ID and API key, with a test-connection button that calls `GET /accounts/{id}`.
  - Gemini API key, or Vertex.
  - Model.
  - Sheet ID, with a check that it is shared with the service account.
  - Skill editor: upload or edit SKILL.md, creating a new version. A "dry-run on fixtures" button runs the skill against the mock receipts.
  - Poll interval and write-back toggles.
  - Keys are write-only in the UI and stored in Secret Manager as `tenant-{id}-payhawk` / `tenant-{id}-gemini`. Locally they go in `.env` or `secrets.local.json`.
- **JSON API:**
  - `GET /api/reviews`
  - `GET /api/reviews/{id}`
  - `POST /api/reviews/{id}/action`
  - `POST /api/runs/poll`
  - `POST /api/runs/decide`
  - `GET /api/runs` (last runs, counts, errors)
  - `GET /api/receipts/{expense_id}/{file_id}` (proxied from GCS)
- **Auth:** IAP on Cloud Run with `--iap`; no auth on localhost.

## 10. Mock mode (default) → live mode

The whole flow must run with **no Payhawk access**: polling, receipt download, extraction, rules, dashboard, sheet, and write-back. The mock is a stand-in for the Payhawk API, not a shortcut around it. The production `PayhawkClient` talks to it over HTTP exactly as it would talk to `api.payhawk.com`, so live mode differs only in the base URL and the API key.

**Mock Payhawk API** (`app/payhawk/mock.py`):
- A FastAPI router mounted in the same app at `/mock-payhawk`. The client's base URL is then `http://localhost:8080/mock-payhawk/api/v3/accounts/demo_account`.
- **Same contract as the real API:**
  - Same paths and verbs, and the same `{items, total}` envelope.
  - The `$filter`, `$skip`, `$take` and `$orderBy` query parameters are honoured. The filter is day-granular on dates, as in the real API.
  - Same `{code, message}` errors.
  - The `X-Payhawk-ApiKey` header is required; any non-empty key works, e.g. `demo-key`.
  - Same business rules: `PATCH` returns 400 unless the expense is `draft`, and supplier and category are accepted only as IDs.
- **Endpoints mirrored:**
  - `GET /accounts/{id}`
  - `GET /expenses`, `GET /expenses/{id}`
  - `GET /expenses/{id}/files`, `/files/{fileId}`, plus the bytes behind `file.url`
  - `GET /expenses/{id}/payments`, `/workflow`
  - `PATCH /expenses/{id}`, `POST /expenses/{id}/status`, `PATCH /expenses/{id}/custom-fields/{cfId}`
  - `POST /comments`, `GET /comments/expense/{id}`
  - `GET /expense-categories`, `GET|POST /suppliers`, `GET /users`, `GET /custom-fields`
- **Contract check:**
  - Payhawk's OpenAPI spec (`api.payhawk.com/api/v3/docs.json`) is saved as `contracts/payhawk-v3.json`.
  - `tests/test_mock_contract.py` checks every mock response against the spec's schemas, so the mock can't drift from the real field names.
- **Raw data:**
  - `fixtures/` holds the 14 expenses, their receipts and expected verdicts.
  - In M1, the generator is extended with matching categories, suppliers, users, payments and custom fields.
- **Simulation controls** (mock only, the same idea as the prototype's `/__log`):
  - `GET /mock-payhawk/__log` lists every write call received.
  - `POST /mock-payhawk/__reset` restores the fixtures.
  - `POST /mock-payhawk/__arrive?n=3` releases the next N expenses (bumping `createdAt` and `modifiedAt`), so polling sees new receipts come in over time.
  - `POST /mock-payhawk/__edit/{id}` simulates an employee editing an expense, so a re-review is triggered.

**Other dependencies in mock mode:**

| Dependency | Mock / local | Live |
|---|---|---|
| Payhawk | mock router above | `https://api.payhawk.com` with the tenant's API key |
| Gemini | `LLM_MODE=replay`: recorded responses in `fixtures/llm/`, so it runs with **zero keys** | `LLM_MODE=live`: Gemini key or Vertex |
| Google Sheet | dashboard + `GET /api/export.csv` (same columns) when no sheet is set | real sheet shared with the service account |
| Firestore / Secret Manager / GCS | Firestore emulator, `.env` / `secrets.local.json`, local `data/` folder | GCP services |

**Switching to live:**
1. In `/settings`, enter the account ID and API key.
2. "Test connection" (`GET /accounts/{id}`) must pass.
3. The tenant then flips to `live`, with `writeback.dry_run` still on.
4. After the first verified run against the real account, you turn `dry_run` off.
5. The dashboard shows a **MOCK** / **LIVE** badge at all times.

## 11. Local development and deployment

- **`docker compose up`:** starts the app (in mock mode, with no keys needed) and the Firestore emulator. The mock is already inside the app, so there is no extra container.
- **Sheets locally:** optional. If no sheet ID is set, the sheet sync is skipped and the dashboard plus CSV export are used. To use a real test sheet, log in with `gcloud auth application-default login` with the Sheets scope.
- **Dockerfile:** `python:3.12-slim` with uv, started via `uvicorn app.web:app --port ${PORT:-8080}`. Jobs use the same image with a different command.
- **CI/CD (`.github/workflows/deploy.yml`):** runs `pytest` on PRs. On a push to `main` it authenticates with Workload Identity Federation (`google-github-actions/auth@v3`), deploys from source with `deploy-cloudrun@v3` (service plus two jobs), and sets up the Scheduler. The one-time GCP setup is a script in `infra/bootstrap.sh`, and you provide the project values later.
- **Gemini config:** `GOOGLE_API_KEY` for AI Studio, or `GOOGLE_GENAI_USE_ENTERPRISE=True` plus a project and location for Vertex. The model is always set explicitly, because ADK's default model is deprecated.

## 12. Tests

- **`tests/test_checks.py`:** each deterministic check, with edge cases at exactly 2%, exactly $10 and month boundaries.
- **`tests/test_pipeline_fixtures.py`:** runs the full pipeline against `fixtures/`, using the mock Payhawk server and recorded Gemini responses, and asserts against `fixtures/expected.json` (status, flags, duplicate_of, fixes, action). With `--live-llm` it calls real Gemini and becomes the regression suite whenever a skill or model changes.
- **`tests/test_mock_contract.py`:** every mock response is validated against `contracts/payhawk-v3.json`.
- **`tests/test_writeback.py`:** checks the right Payhawk calls per intent (draft vs ready, idempotent comments, dry-run).
- **`tests/test_sheets.py`:** the upsert never touches `action`.
