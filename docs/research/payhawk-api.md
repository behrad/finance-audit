# Payhawk public API (v3) and Payhawk MCP: research notes

Researched 2026-11-05. Primary sources only. Most facts come from the machine-readable OpenAPI 3.1 spec behind the developer portal, which I downloaded and parsed directly:

- **[SPEC]** = `https://api.payhawk.com/api/v3/docs.json` (OpenAPI 3.1.0, `info.version: v3`). The portal https://developers.payhawk.com is a Swagger UI. Its config at https://developers.payhawk.com/config/swagger-ui.yml lists this spec as the only one ("API Version 3").
- **[DEVAPI]** = https://payhawk.com/help/overview-of-the-payhawk-developer-api (updated 2026-10-27)
- **[DEVFAQ]** = https://payhawk.com/help/faq-on-payhawk-developer-api
- **[999]** = https://payhawk.com/help/api-returns-only-999-results
- **[MCP-CONNECT]** = https://payhawk.com/help/connecting-payhawk-mcp
- **[MCP-TOOLS]** = https://payhawk.com/help/payhawk-mcp-tool-reference
- **[MCP-ABOUT]** = https://payhawk.com/help/payhawk-mcp-overview
- **[MCP-TROUBLE]** = https://payhawk.com/help/troubleshooting-the-payhawk-mcp
- **[PROBE]** = live unauthenticated HTTP probes I ran on 2026-11-05. Each one is shown with the URL it hit.

Spec paths below omit the prefix `/api/v3/accounts/{accountId}` where that is obvious.

## 1. Authentication

- **Mechanism:** API key only. There is no OAuth for the REST API. The spec has exactly one security scheme, `PayhawkApiKey`: `type: apiKey`, `in: header`, `name: X-Payhawk-ApiKey`. [SPEC `components.securitySchemes`]
- **Alternative header:** `Authorization: Bearer <API_KEY>` is also accepted. [DEVAPI §Authenticating]
- **Creating keys:** In the Web Portal, go to Settings > Integrations > Available integrations > "API connection" > Connect. Pick a scope, enter the details, then click Create. You can copy and regenerate keys afterwards. [DEVAPI]
- **Scopes:** There are only two: **Full access** or **Read-only access**. Each key shows its access level. A read-only key returns "forbidden" errors on writes. [DEVAPI] There are no finer-grained scopes. UNVERIFIED that none exist beyond these two (none are documented).
- **System keys:** "API Primary" and "API Secondary" keys are generated by the system during account setup and cannot be deleted. Payhawk recommends creating a custom key. [DEVAPI]
- **Who can manage keys:** Payhawk Administrator, IT Administrator, or a custom role with "View developer API access" plus "Manage external integrations". [DEVAPI]
- **Per account vs per group:** Keys are account-specific. [DEVAPI] `GET /api/v3/accounts` "with API Key auth returns just the account associated with the api key". [SPEC] Master data for a Payhawk **group** (multi-entity) needs a separate group-level API key and the `/api/v3/groups/{groupId}/...` endpoints. Expenses and payments stay entity-level. [DEVFAQ; DEVAPI §Managing custom fields]
- **Sandbox:** "Payhawk Labs Sandbox accounts" are "standard demo environments, with no expiration date". Admins activate one under Settings > Payhawk Labs > Activate. A sandbox is a single entity and does not support group features. [https://payhawk.com/help/activating-beta-features-in-sandbox-account] UNVERIFIED: whether a sandbox can issue API keys, and whether it uses the same API host. No separate sandbox base URL is documented.

## 2. Base URLs, versions, accountId

- **Host:** The spec's `servers` array is empty [SPEC]. The docs use both `https://api.payhawk.com/api/v3/...` and `https://api.payhawk.io/api/v3/...` [DEVAPI]. Both hosts answer `/api/v3/accounts` with 401 and `/api/v3/rsa-public-key` with 200. [PROBE: `curl https://api.payhawk.com/api/v3/accounts`, `https://api.payhawk.io/...`] Use `https://api.payhawk.com` because the spec is served from it.
- **Versions:** v3 is the only version published in the portal [swagger-ui.yml]. v2 still shows up once, in the webhook signature sample, which fetches `https://api.payhawk.io/api/v2/rsa-public-key` [DEVAPI]. There is no v2 spec: `https://api.payhawk.com/api/v2/docs.json` returns 404 [PROBE]. Use the v3 `GET /api/v3/rsa-public-key` [SPEC].
- **Prototype base `/api/v3/accounts/{accountId}`:** CORRECT. [SPEC paths]
- **accountId:** A string slug that identifies one Payhawk entity (company), taken from the portal URL `https://portal.payhawk.com/?account={accountId}`, for example `payhawk_demo_6fc0db9a`. [DEVAPI] `IAccount` = `{id, name, uic, vat?, baseCurrency, group?{id}}`. [SPEC `IAccount`] You can discover it with `GET /api/v3/accounts`. [SPEC]

## 3. Listing and fetching expenses

`GET /api/v3/accounts/{accountId}/expenses` returns `IExpensesResponse = { items: IExpense[], total: number }`. `total` is the count across all pages. [SPEC]

Query parameters [SPEC]:

| Param | Meaning |
|---|---|
| `$filter` | URL-encoded **JSON** object matching `IExpenseFilter`. Supports `$and` / `$or` |
| `$orderBy` | URL-encoded JSON **array with at most 1 element**, e.g. `[{"createdAt":"asc"}]` |
| `$skip` | Offset pagination |
| `$take` | Page size. The spec says "maximum number of items that will be returned is 10000" |

**Page size conflict:** The help center says the page size is 1,000 per request [DEVAPI §Page size; 999]. The spec says the maximum is 10000 [SPEC]. Assume 1000, page with `$skip` until you reach `total`, and confirm against a real account. Pagination is offset-based only. There is no cursor. [SPEC]

**Filterable fields** (`IExpenseFilter`) [SPEC]:
- `id` (`$equal`, `$in`; pattern `^[0-9]+$`, so ids are numeric strings)
- `status` (`$equal` one of `archived|draft|ready`)
- `createdAt`, `modifiedAt`, `settledAt`, `reviewedAt` (`$equal|$lessThan|$greaterThan|$empty`)
- `title`, `type` (`$equal|$notEqual|$contains|$empty`)
- `category.id`, `createdBy.id`, `owner.id`
- `document.documentDate|dueDate|serviceDate` (date ops), `document.documentNumber` (`$contains|$empty`)
- `reconciliation.baseTotalAmount` (numeric ops)
- `supplier.name`, `card.id`, `purchase.id`
- `export.status` / `payment.export.status` (`succeeded|failed|not-exported|pending`), `export.into`, `payment.export.into`

There is **no filter on `approvalProcess.status`**. [SPEC]

**Incremental polling:** `modifiedAt` exists both as a filter and as a field. However, "Filtering by Date fields ignores *time* data and compares by *date* part only" [SPEC, `$filter` description]. That makes `modifiedAt > lastRun` day-granular. Poll with `modifiedAt $greaterThan <yesterday>` and dedupe on `id` plus `modifiedAt` on the client. `$lessThan` / `$greaterThan` look exclusive. The help center sample also uses `$greaterThanEqual` for bank statements [DEVAPI], but `IExpenseFilter` has no such operator [SPEC]. UNVERIFIED: whether `$greaterThan` on a date excludes the boundary day.

**Sorting:** Only `id`, `createdAt`, `settledAt` (asc/desc) [SPEC `IExpenseOrderBy`]. You cannot sort by `modifiedAt`. The help center writes the param as `orderBy=` without the `$` [DEVAPI]. The spec name is `$orderBy`.

**Single expense:** `GET .../expenses/{expenseId}` returns `IExpense`. [SPEC]

## 4. Expense schema (`IExpense`)

Required fields: `id, createdAt, createdBy, type, status, isPaid, title, lineItems, reconciliation, externalLinks`. [SPEC `IExpense.required`]

| Field | Type / values | Notes |
|---|---|---|
| `id` | string (numeric) | IDs are never reused after deletion [DEVFAQ] |
| `title` | string | User-friendly title |
| `note` | string? | Expense note. There is no separate "description" field |
| `type` | enum `bank, card, cash, cashInAdvance, mileage, reimbursable, perDiem` | |
| `status` | enum `archived, draft, ready, deleted` | **Review state**, not approval. `ready` = reviewed (see §6) |
| `approvalProcess` | `{status: draft\|pending\|approved\|rejected\|cancelled, firstSubmittedAt?, submittedAt?}` | **This is where pending/approved/rejected lives** |
| `isPaid` | boolean | |
| `createdAt`, `modifiedAt?`, `settledAt?`, `reviewedAt?` | date-time | |
| `createdBy`, `reviewedBy?`, `owner?` | `IActor {id, email, firstName?, lastName?, externalId?}` | `owner` is present only when a real user owns the expense. **No `name` field** |
| `category?` | `{id, name?, fullName?, parentId?, accountCode?, createdAt?, managers?[{userId}]}` | |
| `item?` | `{id, name, code?, externalId?}` | Used instead of a category on some accounts |
| `supplier?` | `IExpenseSupplier {id?, name?, taxId?, vat?(deprecated), uic?, countryCode?, address?, postalAddress?, externalId?, externalSource?, contactName/Email/Phone?, customFields?, status?(active\|archived), bankAccounts?}` | |
| `reconciliation` | `IReconciliation` | **Holds the amounts.** See below |
| `taxRate?` | `{name, code, rate, type?(standard\|reverse_charge\|withholding), config?}` | |
| `taxDetails?`, `withholdingTaxRateCode?` | | |
| `lineItems` | `ILineItem[]` | Each has `id, categoryId?, category?(name), item?, reconciliation, taxRate?, note?, amortization?, purchase?, purchaseItem?` |
| `lineItemsVersion?` | string | Optimistic-concurrency token for `PATCH .../line-items` |
| `document?` | `IExpenseDocument` | See below |
| `externalLinks` | `[{title, url}]` | |
| `perDiem?`, `mileage?`, `amortization?`, `purchases?`, `purchase?`, `purchaseItem?`, `expenseReport?{id}`, `linkedDocuments?[]` | | |

All of the above comes from [SPEC `IExpense` and the referenced schemas].

**`IReconciliation`** (on the expense and on each line item) [SPEC]:
- `totalAmount?`, `taxAmount?`: in the **paid/expense currency**
- `currency?`: the expense currency
- `baseTotalAmount?`, `baseTaxAmount?`: in the **account base currency**, "calculated against the official exchange rate"
- `baseCurrency` (required)
- `fxRate?`: rate to the Payhawk base currency
- `fxRateToPaymentCurrency?`: used when the payment currency differs
- `customFields?[]`: `{id, label, value?, externalId?, externalSource?, selectedValues?[{id, label, externalId?, owner?, parentId?, childId?}]}`
- `accountCode?`, `quantity?`, `unitPrice?`, `withholdingAmount?`, `selfAssessedAmount?`

Custom fields therefore live at `reconciliation.customFields`, not at the top level.

**`IExpenseDocument`** [SPEC]:
- `documentDate?`, `documentNumber?`
- `documentType?` (`receipt|invoice|proforma|credit_note`)
- `serviceDate?`: "Date indicating the service period". There is **no `serviceEndDate`**.
- `dueDate?`, `discountAmount?`, `discountDueDate?`
- `files: IFile[]`

**Payment-level original amounts:** `GET .../expenses/{id}/payments` returns `IExpensePayment {id, type(bank|card), status(pending|settled|failed|reverted|expired), amount, currency, originalAmount, originalCurrency, fxRate, fees{fx,pos,bank}, date, description, cardId?, cardLastDigits?, merchantCountryCode?, fundAccountId, fundAccountType, expenseIds[]}`. [SPEC] Payment details: `GET .../payment-details` returns `{currency?, paymentScheduledAt?, paymentReference?, paymentDate?, paymentSource?, paymentDetailsConfirmed?}`. [SPEC]

**Approval workflow:** `GET .../expenses/{id}/workflow` returns `IExpenseWorkflowStatus {approvalStatus, approvedAt?, approvedBy?(IActor), reviewedAt?, reviewedBy?}`. [SPEC] The help center says this response has a `steps[]` array with `user.name` and `status` [DEVAPI §Retrieving the approver's name], but the spec has **no `steps`**. This is a docs mismatch. UNVERIFIED.

**Export/reconciliation status:** Use `GET .../expenses/{id}/export-history` [SPEC], or the `export.status` filter. [SPEC; DEVFAQ]

**Payhawk OCR data:** Payhawk does run OCR/AI extraction and fills fields such as total, invoice number, document date and supplier [https://payhawk.com/help/automatic-population-of-expense-field-data]. The API does **not** expose the raw extracted values separately: the spec contains no `ocr`/`extracted` fields [SPEC, text search]. You only see the resulting field values, which may be OCR-filled or user-edited, and you cannot tell which.

## 5. Files and receipts

- `IFile = {id, fileId, url, contentType, generatedFileUrl?, generatedFileContentType?, externalSource?, externalId?}`. `url` is described as "Download url of the file". `fileId` is the "Public identifier of the file in Payhawk". `generatedFile*` is "used for eInvoices". [SPEC]
- Files appear inline at `expense.document.files[]`. [SPEC; DEVAPI §Retrieving the invoice]
- `GET .../expenses/{expenseId}/files` returns `{items: IFile[], total}`. [SPEC]
- `GET .../expenses/{expenseId}/files/{fileId}` returns **IFile metadata as JSON, not bytes**. The path parameter is the **public `fileId`**, not `id`. [SPEC] Download the bytes from `url`.
- Upload: `POST .../expenses/{expenseId}/files` (multipart/form-data, `IFileUpload`). Delete: `DELETE .../files/{fileId}`. [SPEC]
- Webhook `expense.document.converted` carries `originalFile{id, contentType, url}` and `convertedFile{...}`. Payhawk converts attachments to PDF. [SPEC `IWebhookExpenseDocumentConvertedData`; DEVAPI event table] Expect both images and PDFs and branch on `contentType`.
- UNVERIFIED: whether `url` is a pre-signed, expiring URL or needs the `X-Payhawk-ApiKey` header, and which host it points at. The spec does not say.

## 6. Write operations

| Goal | Endpoint | Body | Notes |
|---|---|---|---|
| Patch supplier / category / note / doc number / doc date / tax rate / amortization | `PATCH .../expenses/{expenseId}` | `IExpensePatch {supplier?{id}, category?{id}, taxRate?{id}, note?, documentNumber?, documentDate?, amortization?{label?, externalId?, startDate?, endDate?}, externalLinks?[]}` returns IExpense | **Allowed only while the expense is a draft (not reviewed).** Reviewed/archived/deleted expenses return 400. `externalLinks` must be sent **alone**, and is allowed after review/export. Supplier and category take **IDs**, not names. [SPEC] Not patchable: amounts, currency, documentType, serviceDate, owner |
| Set a custom field | `PATCH .../expenses/{expenseId}/custom-fields/{customFieldId}` | `{selectedValues?: [...]} \| {value?: string\|null}` returns 204 | Applied to all line items when they exist [SPEC] |

A read-only key cannot do any of these. [DEVAPI]

## 7. Webhooks

- Endpoints: `POST .../webhooks` with `{eventType, callbackUrl (HTTPS)}` returns 201 `{id, eventType, callbackUrl, createdAt, status: active|deactivated_by_payhawk|deactivated_by_user}`. Also `GET .../webhooks`, `GET|DELETE .../webhooks/{subscriptionId}`. [SPEC] One subscription covers one event type.
- Event types in the spec: `expense.created, expense.reviewed, expense.approved, expense.rejected, expense.deleted, expense.paid, expense.payment-details.updated, expense.document.uploaded, expense.document.converted, payment.authorized|reverted|settled|failed, deposit.received, supplier.created|updated, purchase-order.updated|status.changed|identifier.assigned|receipt-note.added, one-time-login-request.completed, expense-report.reviewed|deleted|expenses.updated`. [SPEC `INewWebhookSubscription.eventType`] The help center table lists a subset. [DEVAPI]
- **There is no `expense.updated` event.** Edits such as a category change do not fire a webhook. That makes webhooks a trigger, not a full replacement for polling. [SPEC enum]
- Payloads are thin. Envelope: `{id (delivery id), accountId}` [SPEC `IWebhookNotificationEnvelope`]. Data: `IWebhookExpenseData {expenseId}`. `expense.document.uploaded` adds `{fileId, fileType?(trip-document|file-upload), contentType?, fileUrl?}`. [SPEC] UNVERIFIED: how the envelope and data are nested on the wire. The spec envelope lists only `id` and `accountId`, and the help center shows the sample only as an image.
- Retries happen on 408, 409, 429 and 5xx, not on 400. [DEVAPI]
- **Signature:** header `X-Payhawk-Signature`, "SHA256 encrypted via RSA". You verify `"${timestamp}:${url-path-with-query}:${rawBody}"` with the public key from `GET /api/v3/rsa-public-key` (text/plain, no auth). [DEVAPI; SPEC] UNVERIFIED: **which header carries the timestamp.** The sample uses an undefined `timestampString`. Also unverified: the signature encoding (base64?) and the exact padding (PKCS1 v1.5, assumed from the node-rsa default). Confirm by capturing a real delivery.
- Webhooks can be auto-deactivated (`deactivated_by_payhawk`). [SPEC] Re-check subscriptions periodically.

## 8. Rate limits, errors, idempotency

- **15 requests/second, sliding window.** 429 responses carry `Retry-After` and `RateLimit-Remaining`. [SPEC, 429 description; DEVAPI] Live response headers: `ratelimit-policy: 15;w=1`, `ratelimit-limit`, `ratelimit-remaining`, `ratelimit-reset`, plus `x-ratelimit-*`. [PROBE: `curl -i https://api.payhawk.com/api/v3/accounts`]
- **Error body:** `IError {code: string, message?: string}`. Example: `{"code":"Unauthorized","message":""}`. [SPEC; PROBE] Statuses used: 400, 401, 403, 404, 429. [SPEC]
- **Idempotency:** The only mention is on `POST .../expenses` (create): an `Idempotency-Key` header is supported, except for per-diem expenses. [SPEC, Create expense description] PATCH and status endpoints document no idempotency. Make them idempotent yourself by checking current state first.
- Responses include `x-internal-correlation-id`, which is useful for support tickets. [PROBE]

## 9. Payhawk MCP server (official)

- **It exists and is official:** announced in Fall '26 and available to all customers. [MCP-ABOUT; https://payhawk.com/help/fall-26-edition.md]
- **URL:** `https://mcp.payhawk.com/mcp`. [MCP-CONNECT]
- **Transport:** remote **Streamable HTTP**. Claude Code setup: `claude mcp add --transport http payhawk https://mcp.payhawk.com/mcp`. [MCP-CONNECT] There is no stdio package. The `payhawk` GitHub org has only 3 forked repos and no MCP or SDK (https://api.github.com/orgs/payhawk/repos). npm and PyPI have no Payhawk-published package (https://registry.npmjs.org/-/v1/search?text=payhawk, https://pypi.org/pypi/payhawk/json returns 404).
- **Auth:** OAuth 2.1 with PKCE and **Dynamic Client Registration**, signed in as an **individual user** with their Payhawk portal login. You see only what that user can see. [MCP-CONNECT; MCP-ABOUT] Unauthenticated `POST /mcp` returns 401 with `WWW-Authenticate: Bearer ... resource_metadata="https://mcp.payhawk.com/.well-known/oauth-protected-resource/mcp"`. The AS metadata at `https://mcp.payhawk.com/.well-known/oauth-authorization-server` lists `/authorize`, `/token`, `/register`, `/revoke`, grant types `authorization_code` and `refresh_token`, and PKCE `S256`. [PROBE] Sessions need a new sign-in after 7 days idle and every 30 days at most. [MCP-CONNECT]
- **Client allowlist:** "Payhawk accepts sign-ins only from the AI Assistants in the table". Any other app fails with `host-not-allowed` or "The client redirect URI is not allowed". [MCP-CONNECT; MCP-TROUBLE] The table covers Claude, Claude Code, ChatGPT, Codex CLI, Cursor, GitHub Copilot, MS Copilot Studio / M365 Copilot, Langdock, Notion and Dust. Gemini and Google ADK are not listed. [MCP-CONNECT]
- **Tools** (names only; the tool list is filtered by role) [MCP-TOOLS]:
  - Expenses: `list_expenses, get_expense, get_expense_approval_status, list_expense_payments, list_documents, upload_document, ingest_and_auto_match_receipt, create_expense, get_invoice_inbox, submit_expense, recode_expense, list_close_blockers, list_expense_reports, get_expense_report, list_expense_subscriptions, confirm_expense_subscription, manage_expense_subscription, list_mileage_claims`
  - Approvals: `review_queue, needs_my_attention, get_approval_request, approve_or_return, complete_expense_review, return_expense_for_review, list_audit_logs, out_of_office_delegate`
  - Reference data: `list_suppliers, get_supplier, manage_supplier, list_account_codes, list_tax_rates, list_custom_fields, list_expense_categories, get_expense_category, list_users, get_user, list_teams, list_team_members, list_accounts`
  - Other: `add_comment, list_comments, insights_query_async, get_job_status`, plus cards, POs, budgets, playbooks, `product_help`, `submit_feedback`
  - **Input/output schemas are not published.** UNVERIFIED. They are only available via `tools/list` after OAuth.
- Write tools show a preview and wait for user confirmation. The MCP never starts payments, masks card numbers to the last 4 digits, and redacts personal details in listings. [MCP-ABOUT]
- **Usable from Google ADK `MCPToolset`?** Not in practice for an unattended service. ADK can speak Streamable HTTP, but (a) the OAuth redirect-URI allowlist blocks clients that are not on the list [MCP-TROUBLE], (b) auth is per human user with a 30-day maximum session, not a service credential [MCP-CONNECT], and (c) write tools are designed around interactive human confirmation [MCP-ABOUT]. Conclusion: use the REST API with an API key for the backend service. UNVERIFIED whether Payhawk would allowlist a custom client on request. The docs say to contact support@payhawk.com. [MCP-CONNECT]

## Gaps and risks

**Mismatches with the prototype shape**
1. `status` pending/approved/rejected is **wrong**. `status` is `archived|draft|ready|deleted`, where `ready` = reviewed. Approval lives in `approvalProcess.status` (`draft|pending|approved|rejected|cancelled`). [SPEC]
2. `amount{value,currency}` and `total{value,currency}` **do not exist**. Use `reconciliation.totalAmount` + `reconciliation.currency` (expense currency) and `reconciliation.baseTotalAmount` + `baseCurrency` (account currency), plus `fxRate`. Original card amounts are on `/payments` (`originalAmount`, `originalCurrency`). [SPEC]
3. `owner{id,name,email}`: there is **no `name`**. Use `firstName` + `lastName`. `owner` is optional. [SPEC]
4. `supplier{name}` is fine but incomplete. It also has `id` (needed to PATCH), `taxId`, `countryCode`, etc. [SPEC]
5. `category{name}`: it also has `id` (needed to PATCH) and `fullName`. Some accounts use `item` instead. [SPEC]
6. `document.serviceEndDate` **does not exist**. There is only `serviceDate`; the `amortization.startDate`/`endDate` fields might hold the period (UNVERIFIED). [SPEC]
7. `/files/{id}` is **wrong**. The real paths are `/expenses/{expenseId}/files` and `/expenses/{expenseId}/files/{fileId}`. That endpoint uses the public `fileId`, not `id`, and returns JSON metadata. Download bytes via `file.url`. [SPEC]
8. Missing fields worth using: `title`, `modifiedAt`, `reviewedAt`, `isPaid`, `createdBy`, `lineItems` (per-line category, amount and tax), `reconciliation.customFields`, `taxRate`, `document.dueDate`, `expenseReport`. [SPEC]
9. `$take=1000` is fine, but you must page with `$skip` until `total`. [999]

**Design risks**
- Incremental polling is only day-granular (`modifiedAt` filter ignores time). You cannot sort by `modifiedAt`. Re-fetch a 1–2 day window and dedupe. [SPEC]
- There is no approve/reject REST endpoint. Writeback is limited to review (`status: ready/draft`), submit, comments, custom fields, and draft-only field PATCH. **Once an expense is reviewed, supplier/category can no longer be patched via the API.** Return it to draft first, or act before review. [SPEC]
- There is no `expense.updated` webhook, so webhooks can trigger work but polling is still required. [SPEC]
- 15 req/s across the whole key. File downloads and per-expense `/workflow` calls count against it. [DEVAPI]
- Payhawk's OCR output is not exposed, so you cannot tell user-entered values from OCR-filled ones. [SPEC search]

**Needs a real account to confirm**
- Effective max `$take` (1000 vs 10000).
- Whether `file.url` is pre-signed/expiring or needs the API key, and which content types occur (image/jpeg, image/png, application/pdf, HEIC?).
- Webhook timestamp header name, signature encoding and padding; wire envelope shape.
- `/workflow` response: spec fields vs the help center's `steps[]`.
